写技术博客这件事，看起来简单，但坚持下来的人不多。我观察过一些长期更新的博主，他们有几个共同点。

## 先想清楚为什么写

很多人开始写博客是为了"显得专业"，或者被某个大 V 影响觉得"应该写"。这种动机很难持久。真正能坚持下来的，通常是**为了自己**——为了把刚解决的问题记下来，免得下次再踩坑；为了把模糊的想法写清楚，逼自己理清思路。

如果你写博客的目的是"涨粉"、"变现"，那不如直接去做短视频。博客这种形式，注定是慢的。

## 不要追求完美

我见过太多人，写了三篇就停了，因为觉得"写得太烂"。但博客不是论文，不需要严谨到每个字都推敲。**先写出来，再改**。一篇 60 分的文章发出去，比一篇 90 分的文章永远躺在草稿箱里有价值得多。

GitHub Issues 的好处就是写起来没压力——它本来就是个"提问题"的地方，你提一个"今天踩了个坑"的 Issue，写两段就发了，没人会嫌你短。

## 把"具体"放在第一位

抽象的总结没人爱看。比如：

- ❌ "今天学到了 React Hooks 的精髓"
- ✅ "今天用 `useEffect` 时遇到了一个闭包陷阱，原因是依赖数组没写对，正确的写法是……"

具体到代码、具体到错误信息、具体到解决步骤。一年后回来看，你还能想起来当时发生了什么。

## 标题要能搜到

技术博客的流量主要来自搜索引擎。标题里**带上关键词**：

- ❌ "今天踩了个坑"
- ✅ "React useEffect 闭包陷阱：依赖数组没写对的解决方案"

后者既能在 Google 搜到，也能让你自己以后翻历史时一眼定位。

## 用标签组织，不要用目录

传统的博客喜欢用目录分类（"前端"、"后端"、"运维"），但实际写起来你会发现：一篇文章经常跨多个领域。**标签比目录灵活**——一篇文章可以同时是「React」「调试」「踩坑记录」。

GitHub Issues 的 Labels 天然就是标签系统，配合这个博客主题，会自动生成标签云和标签页。

## 写完就发，不要囤

我以前有个坏习惯：一次写五篇，然后定时发布。结果第二天发现其中三篇有错，又得改。**写完一篇发一篇**，错了再改，比囤着强。

## 结语

写博客这件事，最难的不是写，是开始写。打开你的 GitHub 仓库，新建一个 Issue，把今天遇到的一件小事写下来。哪怕只有 100 字。

一年后回头看，你会感谢现在的自己。
